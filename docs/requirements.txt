2. MEVCUT MANUEL İŞ AKIŞI

Bir KEP bildirimi geldiğinde genellikle iki ayrı dosya/parça bulunuyor:

1. KEP zarfı / bildirim / envelope
2. Asıl evrak / content

Bu iki dosyanın birbirine ait olduğunun doğru şekilde eşleştirilmesi gerekiyor.

Ardından belgelerden dava/dosya bilgileri çıkarılıyor.

Örneğin mümkün olduğunda:

* dosya/esas numarası
* mahkeme
* icra müdürlüğü
* taraflar
* borçlu
* alacaklı
* gönderici
* tarih
* tebliğ tarihi
* belge tipi
* ilgili referans numaraları
* dosyadan çıkarılabilecek diğer önemli alanlar

çıkarılacak.

Daha sonra muhasebeye gönderilmek üzere Excel hazırlanıyor.

Muhasebe dosyaları kontrol edip bir sonuç giriyor. Temel olarak:

* var
* yok

gibi bir sonuç geliyor.

Muhasebenin döndürdüğü Excel tekrar programa import edilecek.

Program ilgili satırları kendi kayıtlarıyla eşleştirecek ve muhasebe sonucunu dosyaya işleyecek.

Sonra bu sonuca göre uygun dilekçe oluşturulacak.

Örneğin farklı “var/yok” durumlarında farklı dilekçe template’leri kullanılabilir.

Template içinde:

* dosya numarası
* taraf
* tarih
* mahkeme
* diğer case field’ları

otomatik doldurulacak.

Uzun vadede dilekçe + vekaletname tekrar KEP üzerinden gönderilecek ve e-imza kullanılacak.

Ancak MVP’de SON GÖNDERİM MANUEL.

3. MVP’DE İSTEDİĞİM AKIŞ

Program açılır.

Kullanıcı yeni batch oluşturabilir.

Örneğin bir klasöre elle indirilmiş KEP dosyalarını programa import eder.

Program:

A. dosyaları tarar

B. dosya tiplerini belirler

C. KEP envelope ile gerçek belgeyi mümkün olduğu kadar otomatik eşleştirir

D. eşleşmeye bir confidence score verir

E. şüpheli eşleşmeleri kullanıcıya gösterir

F. belgelerden gerekli metadata/case field’larını çıkarır

G. kullanıcıya review ekranı sunar

H. onaylanan kayıtları local database’e kaydeder

I. muhasebeye gönderilecek Excel’i oluşturur

Daha sonra:

J. muhasebeden gelen Excel kullanıcı tarafından programa import edilir

K. program satırları kendi case kayıtlarıyla eşleştirir

L. “var/yok” ve diğer muhasebe alanlarını kayıtların üzerine işler

M. ilgili dilekçe template’ini seçer

N. doldurulmuş dilekçeyi oluşturur

O. çıktı klasöründe ilgili dosyanın tüm çıktıları düzenli şekilde saklanır

4. ÇOK ÖNEMLİ: HUMAN-IN-THE-LOOP

Legal workflow olduğu için program sessizce tahmin yapıp yanlış belgeyi yanlış dosyaya bağlamamalı.

Belirsiz durumlarda:

NEVER GUESS SILENTLY.

Örneğin:

* iki envelope aynı belgeye uyuyorsa
* esas numarası farklı okunuyorsa
* PDF metadata ile belge içeriği çelişiyorsa
* muhasebe Excel satırı tek bir case ile eşleşmiyorsa

durum “Needs Review” olarak işaretlenecek.

UI kullanıcıya problemi açıkça gösterecek.

Otomatik işlem ile insan onayı birbirinden ayrılacak.

7. DOSYA YÖNETİMİ

Original imported files ASLA overwrite edilmemeli.

Her import edilen file için mümkünse:

* original filename
* normalized filename
* full path / managed path
* size
* SHA-256 hash
* import timestamp
* detected MIME/type
* relationship to case

sakla.

Duplicate detection için hash kullanılabilir.

Dosya organizasyonu örneğin:

workspace/
database/
originals/
batches/
generated/
exports/
templates/
logs/

gibi olabilir.

Daha iyi bir yapı öneriyorsan değiştir.

8. DOCUMENT MATCHING

Envelope-content matching sistemin kritik parçalarından biri.

Matching sadece filename’e dayanmamalı.

Kullanılabilecek sinyalleri modüler şekilde tasarla:

* filename similarity
* timestamps
* identifiers inside envelope
* identifiers inside actual document
* case number
* sender
* recipient
* reference IDs
* document metadata
* batch proximity
* unique KEP metadata

Matching sonucu örneğin:

matched
ambiguous
unmatched

olabilir.

Ayrıca confidence score olsun.

Matching algorithm strategy olarak ayrı component olmalı.

9. DOCUMENT EXTRACTION

PDF ve diğer belgelerden bilgi çıkarılması gerekiyor.

İlk MVP’de mümkünse önce text-based PDF parsing yap.

OCR’u ilk çözüm olarak kullanma.

Scanned PDF varsa “OCR required / manual review” olarak işaretlenebilir.

Extraction pipeline modüler olsun.

Örneğin:

DocumentLoader
TextExtractor
DocumentClassifier
FieldExtractor
FieldNormalizer
FieldValidator

gibi.

Regex/parser tabanlı extraction ile başlanabilir.

Mahkeme ve dosya formatlarına göre extractor’lar sonradan eklenebilmeli.

Her extracted field için sadece value değil mümkünse:

* source document
* extraction method
* confidence
* original text/snippet

sakla.

10. EXCEL WORKFLOW

Excel export/import çok önemli.

Muhasebeye verilen Excel deterministik olmalı.

Her satırda gizli olmayan ama stabil bir internal record ID bulunması çok faydalı olabilir.

Örneğin:

Record ID
Dosya No
Mahkeme
Taraf
Tarih
…
Muhasebe Sonucu

Muhasebe Excel’i geri geldiğinde önce internal ID ile eşleştirmeye çalış.

ID yoksa fallback matching yapılabilir fakat ambiguity kullanıcıya gösterilmeli.

Import sırasında:

* yeni satır
* kayıp satır
* duplicate ID
* invalid value
* case not found

gibi problemler raporlanmalı.

Excel component’i domain logic’ten bağımsız olsun.
